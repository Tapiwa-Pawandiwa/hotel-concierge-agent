1. Executive summary

This document proposes a concrete build plan for extending the current single-agent RAG concierge (documented in docs/mycheckpoint.html) into the full system designed across an extended scoping conversation: a guest-facing conversational agent covering check-in, ordering, and event inquiries, and a staff-facing operations agent covering intake, routing, approvals, and financial reconciliation — all built on a mocked-enterprise pattern (simulated PMS/POS/ERP/WFM feeds) rather than live third-party integrations, so the whole thing runs standalone.

Everything in this plan reduces to four primitives, repeated at every layer: a who (guest, staff member, or room), a request (something someone wants done), a charge (anything posted to a guest's bill), and a signal (an external event — sensor, lock, payment, mock vendor feed — that creates or updates a request or charge, and carries no logic of its own). Every feature below is an instance of one of these four things, not a new architectural concept.

This is a first draft. Section 11 lists specific defaults that were made unilaterally during design and need explicit sign-off, and Section 4 flags one piece of required foundational work — splitting guests into identity and reservation records — that nothing else in the plan can proceed without.

4. Database architecture

SQL, not NoSQL — and why

This system is SQL throughout — a single Postgres instance (via Supabase) serves both the relational data and, via the pgvector extension, the vector-similarity search behind RAG. No document store and no separate vector database are used.

Almost everything here is relationships, not documents: a guest has reservations; a reservation has bill items; a bill item may reference an order; an order references menu items; an event booking has allocations referencing spaces, rooms, and vendors. Modeling that in a document database means denormalizing the same facts across multiple documents and manually keeping them consistent, or constantly reaching across collections anyway — foreign keys and joins are the natural fit for data this interconnected. Billing specifically needs real ACID guarantees: a payment capture and the guest-bill status it updates cannot be allowed to disagree, and Postgres transactions make "money reconciles, or the whole write rolls back" a property that comes for free rather than something built by hand.

The one piece that might look like a NoSQL/specialized-database job — semantic search over policy documents — doesn't need a dedicated vector database either. pgvector adds a vector column type and distance operators directly to Postgres, so the same database, connection, and backup story serves both jobs. Trade-off worth naming honestly: a dedicated vector database (Pinecone, Weaviate, Qdrant) would out-perform pgvector at very large corpus sizes and offers more specialized indexing. This system's knowledge base is a handful of short policy documents — single-digit thousands of chunks at most, even after every addendum's new policy doc is added — and at that scale, pgvector's simplicity (one engine, one thing to keep alive) wins decisively over the operational cost of a second database purely for embeddings.

5. Knowledge representation & embeddings

Policy knowledge lives as plain markdown files, one per topic, deliberately kept short and single-topic — which is what makes whole-file chunking sufficient today (no paragraph-level splitting logic needed). Ingestion embeds each file with Voyage AI's voyage-3.5-lite model using input_type="document", producing a 1024-dimension vector stored in policy_chunks.embedding vector(1024).

At query time, the guest's question is embedded with input_type="query" instead — Voyage's models are trained to treat "things meant to be searched over" and "things searching with" differently, and using the wrong one quietly degrades retrieval quality without ever throwing an error, so this distinction is easy to get wrong silently. Retrieval itself runs a cosine-distance nearest-neighbor search using pgvector's <=> operator, requiring the query parameter to be cast to ::vector explicitly — Postgres can't infer the type from a bare array inside an ORDER BY. The top matches return to Claude as tool output; Claude, not the retrieval step, decides what to actually tell the guest.

Why Voyage and not Claude directly: Claude doesn't produce embeddings itself — Anthropic's own documentation points to Voyage as the recommended embeddings partner, so this two-vendor pattern is normal, not a workaround.

Why 1024 dimensions: a reasonable middle setting among Voyage's selectable output sizes (256/512/1024/2048), trading nuance against storage and speed. Whatever size is chosen has to match the pgvector column definition exactly, or inserts fail on a dimension mismatch.

Forward-looking: this proposal alone adds several more policy documents (event vendor policy, event deposit/cancellation terms, pool/gym) on top of the existing six. Whole-file chunking stays appropriate as long as each document stays short and single-topic, which has held so far. If any future document grows long or covers multiple sub-topics, it should be split into semantic chunks before ingestion rather than embedded as one large block — worth deciding before a document gets long enough that retrieval quality quietly degrades, not after.

8. Foundational schema refactor (required before Phase 1)

This wasn't explicit in any single design addendum, but every downstream tool assumes it exists: booking_reference is used throughout (check-in, checkout, modify/cancel, group bookings) but there is currently no table that owns it. The Kaggle-derived guests table conflates guest identity with a single stay's attributes into one flat row — it has no concept of a guest having more than one reservation.

Proposed split: guests keeps identity fields only (name, email, country — plus guest_notes from Addendum F for allergies/preferences). A new reservations table becomes the actual home for booking_reference (primary key), guest_id (FK), room_type_id, check_in_date, check_out_date, adr, status (confirmed/checked_in/checked_out/cancelled), and a nullable group_booking_id pointing at event_bookings for the conference-room-block case in Addendum G. The existing 300 synthetic rows migrate cleanly — one reservation per existing guest row — so no seed data is lost, it's just correctly normalized.

Every tool signature already written in the design (check_in_guest(booking_reference), create_booking(...), modify_booking(booking_reference, ...)) depends on this table existing. It's listed here rather than folded silently into Phase 1 because it's easy to miss — nothing "new" was ever said about it, it was just assumed.

Acceptance criteria for the eval suite — not just "15-20 conversations exist." Scenarios are split across five categories, not picked ad hoc: (1) simple Tier-1 lookups (policy question, guest profile) — target 100% pass, these have one correct answer; (2) Tier-2 writes (place an order, book a table) — target ≥90% pass, judged on both the right tool being called and the right arguments; (3) Tier-3 confirmation-gated actions (cancel a booking, process a payment) — target 100% pass on never executing without confirmation, since this is a safety property, not a quality one, plus ≥90% on completing correctly once confirmed; (4) multi-turn handoffs between agents (guest submits an event inquiry → sales_agent generates a quote → staff approves) — target ≥85% pass, the lowest bar deliberately, since this is the newest and most failure-prone path (§6); (5) adversarial/edge cases (guessed guest IDs per R2, ambiguous requests, a guest asking for something Tier 3 without going through the confirmation flow) — target 100% pass on refusing/escalating correctly. 11. Tool & agent inventory (risk-tiered)

Tier 1 = read-only, fully autonomous. Tier 2 = writes, logged and reversible. Tier 3 = touches money/dates/real bookings, human-confirmed before it executes.

Tool-calling conventions. ADK generates the JSON schema each tool exposes to Claude directly from the Python function's type hints and docstring — there's no hand-written schema layer, which means naming and docstring quality is a real reliability lever, not documentation polish. Three conventions apply across every tool listed below:

  • Return-value contract. Every tool returns a consistent {status, data, error} shape rather than raising exceptions or returning ad hoc structures — chosen specifically because R1's failure mode (a missing method call and an invalid cast, both silent until runtime) is exactly what an inconsistent contract lets slip through. A tool that fails returns a structured error the model can react to, not a stack trace.
  • Idempotency. Every Tier 2/3 write tool takes an idempotency key parameter, reusing the same key the client-side write-ahead queue (Addendum D) already generates — so a queued write that replays after a reconnect can't double-charge or double-book.
  • Confirmation mechanism — hybrid, not uniform. Per Section 7: simple yes/no Tier 3 actions use ADK's native require_confirmation; anything needing an editable structured response (event quote approval) uses a hand-built pending_approvals table instead, since ADK's native confirmation flow doesn't support DatabaseSessionService and this project keeps session state in the database.
  • Tool granularity. Narrow, single-purpose tools (modify_booking, cancel_booking, create_booking as three tools rather than one tool with an action enum) — more tools to maintain, but each has an unambiguous name and docstring for the model to match against, which matters more as concierge_agent's tool count grows.

A fourth category of tool call isn't in the tables below: agent handoff itself. transfer_to_agent/AgentTool between the three agents is implemented as a tool call in ADK's schema, same mechanism as everything else.

Guest Profile Management (revised 2026-08-12 — supersedes an earlier draft of this note). Reviewed against external industry sources: MobiDev's hotel-AI integration guide, Profitroom's product interview, an independent AutoGen-based hobby build, and — after direct pushback on the first pass — real-world PMS guest-profile behavior (Cloudbeds' match-confidence search, OPERA Cloud's profile merge rules). The first version of this note treated "walk-in support" as a staff-dashboard/Phase-6 problem and concluded there was nothing to fix yet. That was wrong, caught by checking the actual signatures: create_booking requires an existing guest_id, and verify_guest_identity requires an existing booking_reference — so no path existed anywhere in the design for a person with neither (a true walk-in, or a first-time online guest) to enter the system at all. That's not a Phase 6 gap; it's missing from this phase's own guest-lifecycle scope.

The fix follows the real hotel flow, not an ad hoc "register the walk-in" patch: a guest profile (guests — a Who, Principle II) and a stay (reservations — a Request) are separate primitives, and the standard sequence is always search-for-existing-profile before create-new, for every channel — online, phone, or a human at a desk — not something specific to walk-ins. search_guest_profiles/create_guest_profile/update_guest_profile are the resulting first-class trio, sitting ahead of create_booking rather than folded into it, so the Who/Request boundary and each tool's own idempotency contract stay intact. Deliberately declined as speculative for this phase: any scoring/confidence engine (Cloudbeds' 90%+ match confidence) or automatic merge (OPERA's merge rules) — search_guest_profiles returns candidates and leaves the match judgment to the model/guest conversation, the same pattern list_room_types already uses for "a suite with a couch." verify_guest_identity is unaffected and keeps its own separate job — confirming an identity against a known booking_reference, which a walk-in or new online guest doesn't have yet.

This also resolves MobiDev's cited failure mode ("an agent confirms a booking without seeing a recent walk-in") for the availability side specifically: since every channel resolves guest_id through the same two tools and then calls the same create_booking with the same live per-date availability check (T021's helper, shared with list_room_types/T017), there's one source of truth for both "who is this" and "is a room free" — not two paths that can drift out of sync. That single-source-of-truth property is worth preserving explicitly if Phase 6 ever gives staff a separate booking UI: it must call these same tools, not a parallel implementation.

Two other checks against the same sources came back as validation, not gaps: the Tier 1/2/3 confirmation gating (§7) already matches MobiDev's "start assistive → confirmation-gated → autonomous" best practice, and Profitroom's "transactional not just conversational" framing is already the point of create_booking writing real rows rather than just answering questions. Profitroom's "proactively suggest alternative dates when sold out" is a prompt-level behavior for concierge_agent (call list_room_types again with adjusted dates), not a new tool or schema change — noted here so it isn't lost, not scheduled as new work. The AutoGen build (single-purpose, single-shot report scripts per department, no shared tool-calling runtime, no persistence, no confirmation flow) wasn't a source of adopted ideas — it's a useful negative reference for how much this design already does that a "team of agents" demo doesn't: real risk tiering, a real schema behind every tool, and idempotent writes.

17.2 — Migration files
